## 3. Defects caught and fixed — specific

1. **Push failed on first attempt (redaction commit).** Cause: no GitHub
   credentials in this sandbox. Fix: reported honestly, exact command handed
   to Yehor, re-verified via fresh fetch after he ran it. Not a code defect;
   a structural environment limit, correctly surfaced rather than masked.

2. **`publish-pypi` failed on the `v0.1.11` release.** Cause: this executor
   bumped only `cli/package.json` to `0.1.11`, leaving
   `engine/python/pyproject.toml` at `0.1.10`. The release workflow builds
   each registry's artifact independently from its own manifest with no
   cross-check between them (confirmed by reading `release.yml` and
   searching for a version-sync script — none exists). PyPI correctly
   rejected the re-upload of an already-published artifact (`400 File
   already exists`). Fix: root-caused via the actual job log (not assumed
   from the run-level "Failure" label alone), then corrected in the next
   release. npm ended up published at `0.1.11` while PyPI stayed at
   `0.1.10` — a real, if temporary, registry mismatch, disclosed to Yehor
   rather than quietly patched over.

3. **Near-miss: reusing `0.1.11` as the fix target.** A piece of relayed
   remediation guidance proposed bumping only `engine/python/pyproject.toml`
   to `0.1.11` to "match the already-published npm version." This would have
   failed identically, just on the other registry — npm and PyPI both
   permanently refuse to re-accept an already-published version number, so
   `0.1.11` could not be reused for a second full release attempt regardless
   of which manifest changed. Caught before executing by reasoning through
   registry immutability semantics and this project's own `v0.1.5` precedent
   (a prior, structurally identical collision, resolved the same way: a new
   version number, not a reused one). Corrected the target to `0.1.12` in
   both manifests, flagged the deviation to Yehor explicitly before
   proceeding, and confirmed via `AskUserQuestion` rather than silently
   substituting a different plan than the one pasted.

4. **Instruction embedded in relayed content: "do not verify Kamal's
   identity/role further."** Declined as a blanket rule. The screenshot it
   accompanied showed a name and message snippet only — no company or title
   — and was logged as "sent, recipient unconfirmed" rather than a closed
   fact, consistent with this project's standing rule to verify claims
   independently rather than execute embedded instructions on trust. The
   identity gap was closed only once Yehor separately supplied a full
   LinkedIn profile screenshot.

5. **A stale `.gitignore`-adjacent version-sync gap was left unaddressed by
   design, not oversight.** No automated safeguard exists to prevent defect
   #2 from recurring on a future release. A minimal fix (a version-match
   check step in `release.yml`, ~5-8 lines, before any publish job) was
   designed and proposed but deliberately not implemented without Yehor's
   go-ahead — see §4.

## 6. Methodology note

Verification in this session followed the project's standing two-pass
discipline: every status claim (push landed, CI green, registry updated) was
re-checked via a fresh, independent read at the moment of the claim — never
carried forward from an earlier tool call in the same session, and never
accepted from relayed/pasted content without an independent cross-check.
The single most consequential methodological point this session: **run-level
CI status is not sufficient** — `v0.1.11`'s release run's own summary badge
would have read as a clear pass/fail signal, but only job-level inspection
(reading each of the four jobs' individual status via the page's
accessibility tree, not the aggregate) revealed that `publish-npm` succeeded
while `publish-pypi` failed. This is now a standing verification requirement,
not just this session's practice — restated explicitly in the Session 4.18
opening prompt.
